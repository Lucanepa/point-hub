# On site at the board — 23 Oct 2026

Runbook for the visit to the LedBox C0270 (Raspberry Pi 4). It has no uplink in the hall, so it has
been off the tailnet since 02.10. On 21.10 it was deployed from fw13 over its own Wi-Fi (4fa5fba,
tablet app 1.1.1; backup `.deploy-backups/20261021-201506`; drift-check clean before it).

**The one thing that must happen today is §1: the SCHULEN_KTZH login.** It gives the board internet,
and with it the tailnet: from then on everything else in this runbook can run from lenovoserver,
remotely, on another day if need be (never during a match). Games today, Fri 23.10, start at 20:00 in
KWI A, B and C — finish well before warm-up.

Conventions:

- `fw13$` = the Framework 13 in `~/repos/point-hub`, joined to the board's Wi-Fi `ledbox_C0270`. It has
  **no internet** there, and lenovoserver cannot reach it: prepare it at home (§0). The board is
  `pi@172.24.1.1` from it.
- `lenovo$` = a shell on lenovoserver in `~/repos/point-hub`, on branch **`main`** (all of 22.10's
  branches merged, this kit included). It reaches the board as `ssh ledbox` (its tailnet address) **only
  once §1 has given the board an uplink**. Until then, run a `lenovo$` step from fw13 instead, with
  `BOARD=pi@172.24.1.1` and `ssh pi@172.24.1.1` in place of `ssh ledbox`.
- **Expect** = what a good run prints. **If this fails** = what to do instead. **Undo** = rollback.
- Every provisioning script defaults to `--check` (read-only). `--apply` backs up first to
  `/var/backups/ledbox/`; `--rollback` undoes the newest `--apply`. See `provisioning/README.md` §5.
- Secrets are never typed into a command line: scripts ask (use `ssh -t`). `<...>` is a placeholder.
  Never `cat ~/ledbox-bridge/.env` (it holds the Directus token) — only the `grep`s below.
- Mandatory: §0–§7a (the scorer PIN right after the deploy). After that: checks of today's features
  (§7b–§7f), then optional items, one at a time, each with its own undo.

## 1. THE KEY STEP: power on, reach the board, log in to SCHULEN_KTZH (~15 min)

Everything below `--login` costs nothing and can be repeated. **`--login` itself sends the password, and
wrong credentials lock the account for up to 8 hours.** Never retry it and never guess. Run it over the
board's own Wi-Fi, never over Tailscale.

1. **Power on.** The **Netgear USB Wi-Fi stick must be in the board** (it is `wlan1`, the uplink). The
   panel shows POINT HUB, then the crest within ~45 s.
2. **fw13 joins `ledbox_C0270`.** Then:
   ```bash
   fw13$ ssh pi@172.24.1.1 'hostname; date'
   ```
   Expect: the board's name and **today's date and time**. If the date is wrong: open the console on the
   tablet (it sets the board's clock), then check again. A wrong clock makes the login refuse to start.
3. **Free checks, nothing is sent:**
   ```bash
   fw13$ ssh pi@172.24.1.1 bash ledbox-bridge/provisioning/setup-wlan1-client.sh --check   # wlan1 exists
   fw13$ ssh pi@172.24.1.1 bash ledbox-bridge/provisioning/setup-wlan1-client.sh --scan    # SCHULEN_KTZH listed
   ```
   `wlan1 absent` = push the Netgear stick in properly, run `--check` again. SCHULEN_KTZH not listed =
   move the board/stick nearer the hall's access point.
4. **The login, once.** Keep `-t` and the relative path (not `~/`):
   ```bash
   fw13$ ssh -t pi@172.24.1.1 bash ledbox-bridge/provisioning/setup-wlan1-client.sh --login
   ```
   Username: the KWI school account's (ends in `.kwi`; a `1` in it is the digit). The password: typed
   once, by you, at the prompt; it is never written down anywhere else.

   | It prints | Meaning | Do |
   |---|---|---|
   | `=== connected ===` | done; saved as NM profile `hall-login`, rejoins by itself after every reboot | step 5 |
   | `Nothing was sent`, the clock message, `not in range`, `wlan1 absent` | nothing reached the school's server | fix that one thing, run step 4 again |
   | `the SERVER CERTIFICATE was refused — the password was NOT sent` | the board did not trust the server | **stop**; read the log above it together before anything else |
   | `the server REFUSED the credentials` | **a strike was spent** | **stop. Do not run it again.** Read the output together first |

5. **Prove the uplink, then the tailnet:**
   ```bash
   fw13$ ssh pi@172.24.1.1 bash ledbox-bridge/provisioning/setup-wlan1-client.sh --verify   # uplink + NTP OK
   fw13$ ssh pi@172.24.1.1 'tailscale status | head -3'                                      # the board is online
   ```
   On lenovoserver, within 10 minutes: one ntfy message "Scoreboard back online", and
   `lenovo$ ssh ledbox 'hostname'` answers. From here on the `lenovo$` steps work as written.

**If the account's password ever changes:** run `--forget-login` on the board straight away — every
boot would otherwise send the old password and spend strikes.

**If the login cannot be done today** (refused, or no SCHULEN_KTZH in range): the rest of this runbook
still works from fw13 with `BOARD=pi@172.24.1.1`. For internet in the meantime, a phone hotspot:
`ssh -t pi@172.24.1.1 'sudo nmcli --ask device wifi connect "<hotspot SSID>" ifname wlan1'` (delete it
later with `sudo nmcli connection delete "<hotspot SSID>"`). Free_WLAN_KTZH with the SMS login (console
→ Settings ▸ Hall internet) is the other option. Without SSH at all: micro-HDMI + keyboard, local login.

## 2. Image the SD card (+ the spare) — before anything is deployed (~15–30 min)

Plug the USB SD reader with a blank 32 GB card into the **board**, then:

```bash
lenovo$ ssh ledbox 'lsblk -d -o NAME,SIZE,TRAN,MODEL'     # the reader: TRAN usb, ~29.7G — usually sda
lenovo$ SPARE=/dev/sda ./ops/image-board-sd.sh
```

- Reads the card **once**, up to the end of its last partition; the bridge is stopped for it and
  restarted the moment the read is done (also on Ctrl-C). The panel stays lit.
- The encrypted image goes to `nas-ts:/volume1/backups/ledbox-c0270/`; the same read is written to the
  spare and re-read.

Expect:
```
  swap: ...                         ← note what it says; §10.6 acts on it
  OK: nas-ts:/volume1/backups/ledbox-c0270/ledbox-c0270-sd-<stamp>.img.zst.gpg
  manifest: ....txt
  OK: /dev/sda is bit-identical to the image (<sha256>)
```

Then: pull the reader, label the card **"LedBox C0270 clone 2026-10-23 — this board only"**.
Taping it inside the case comes at the end (§14), after deciding which image it should carry.

If this fails: the script says why and changes nothing on the card (it only reads); the .part is
removed. "no public key" → §0.3. "not reachable" → §1. A spare mismatch → do not keep that card,
re-run with the second card. No NAS: `OUT_DIR=<USB disk>` writes the encrypted file there.

**This image is the rollback for everything below.** Recovering from it: put the spare (or a card
written from the image, see the manifest) in the board.

Optional, 5 min, proves the spare boots: power off, swap cards, power on, check the crest and
`ssh ledbox hostname`, power off, put the original back. (Same identity — only ever in this board.)

## 8. Supervision — the board's crash recovery (~10 min, optional but first in line)

One step per run, so each has its own undo. All live at once except the ramoops part of `crashlog`.

```bash
lenovo$ ssh ledbox 'sudo bash ledbox-bridge/provisioning/setup-supervision.sh'            # --check
lenovo$ ssh ledbox 'sudo bash ledbox-bridge/provisioning/setup-supervision.sh --apply watchdog'
```
Expect: `installed the repo's watchdog at /home/pi/ledbox/bin/watchdog` (if the board's was older),
`ledbox-watchdog: enabled / active — it waits 90 s, then logs 'watchdog started'`, and the panel stays
lit. After 90 s: `ssh ledbox 'journalctl -t ledbox-watchdog -n 3'` → `watchdog started`.
If the panel went dark: the script restarts the driver itself; if not, `ssh ledbox 'sudo systemd-run --collect /home/pi/ledbox/bin/startled'`.

```bash
lenovo$ ssh ledbox 'sudo bash ledbox-bridge/provisioning/setup-supervision.sh --apply restart'
lenovo$ ssh ledbox 'sudo bash ledbox-bridge/provisioning/setup-supervision.sh --apply probe'
lenovo$ ssh ledbox 'sudo bash ledbox-bridge/provisioning/setup-supervision.sh --apply hwdog'
lenovo$ ssh ledbox 'sudo bash ledbox-bridge/provisioning/setup-supervision.sh --apply crashlog'
```
Expect, in order: `hostapd: Restart=on-failure`, `dnsmasq: Restart=on-failure`;
`ledbox-bridge-probe: enabled / active`; `now: RuntimeWatchdog=14s, device state active, timeout 14 s, kernel.panic=10`;
`journald: persistent, 64 MB cap` and `appended 'dtoverlay=ramoops'`.
If `hwdog` says another process holds the device: leave it — do not stop that process blind.

Undo: `--rollback` undoes the newest run; repeat to step further back (crashlog → hwdog → probe → …).

Optional proof of the hardware watchdog (a forced kernel crash — no match on, after §2, best after the
§10.7 reboot so ramoops is live): `ssh ledbox 'echo c | sudo tee /proc/sysrq-trigger'` → the board resets
by itself within ~15 s, the crest is back ~45 s later, and `ls /var/lib/systemd/pstore` holds the panic record.

   ```bash
   lenovo$ ssh ledbox 'sudo bash ledbox-bridge/provisioning/setup-cable-dhcp.sh'      # --check
   ```
   Expect: `method=manual addresses=192.168.5.1/24`, `udp/67 on eth0: accepted`, `OK to --apply`.
   If the openvolley Pi is ever cabled to eth0 again: it must keep a static address outside .50–.99 and
   run no DHCP server there (`ssh openvolley 'nmcli -t -f NAME,DEVICE connection show --active'`).
3. Apply:
   ```bash
   lenovo$ ssh ledbox 'sudo bash ledbox-bridge/provisioning/setup-cable-dhcp.sh --apply'
   ```
   Expect: `dnsmasq: active`, `:53 bound on: ... (wlan1 not among them)`.
   Undo: `setup-cable-dhcp.sh --rollback`.
4. **The test**: on the tablet, Wi-Fi **off**. USB-C Ethernet adapter into the tablet, cable into the
   board's network port. Within ~10 s:
   - `ssh ledbox 'grep 192.168.5. /var/lib/misc/dnsmasq.leases'` → one lease in .50–.99.
   - The app loads `http://192.168.5.1:8890` (the "cable" origin) — the console works, points land.
     The https name does not resolve on the cable (no DNS there, by design), so the app falls back to
     that address — which is also what cable trust needs: it holds only for requests that arrive on
     192.168.5.1. A laptop on the cable uses `http://192.168.5.1:8890` too.
   - Over the cable the console opens **without asking for the scorer PIN**; switch the tablet back to
     Wi-Fi (`ledbox_C0270`, cable out) and it **does** ask for it.
   - From a laptop on the cable: `curl -s http://192.168.5.1:8890/api/status | grep -o '"pinTrust":"[a-z]*"'`
     → `"pinTrust":"cable"`.
   - Tablet's Ethernet details: no gateway, no DNS (a default route via the board would send the
     tablet's traffic through the board).
   - Before DHCP is applied (or if step 3 was undone): give the tablet's Ethernet a static
     `192.168.5.60/24` with **no** gateway and no DNS, and the same test applies.
5. Only if all of 4 passed: tick `- [x] Cable (USB-C Ethernet) with Wi-Fi off ...` in `android/README.md`
   (Manual on-device test checklist) and commit it.

## 11. On the glass: driver, refresh, limit_refresh (~30 min, someone watching the panel)

The runtime-brightness `flushBuffer2` and `firmware/flushbuffer/measure-refresh.sh` come from the
driver branch, merged into `main` on 22.10.

1. **Rebuild flushBuffer2** (the new `flushbuffer.cc` reads brightness live): the steps are
   in `firmware/flushbuffer/README.md` → *On the board: rebuild and switch over*, which keeps the
   2026-08-01 binary as the fallback. The build needs two pinned downloads; the board may have no
   internet, so copy them over first (§0.6):
   ```bash
   lenovo$ scp -r firmware/flushbuffer ledbox:flushbuffer-src
   lenovo$ ssh ledbox 'mkdir -p /home/pi/flushBuffer-rebuild' && \
           scp ~/archive/ledbox-research-2026-10-22/flushbuffer-sources/* ledbox:/home/pi/flushBuffer-rebuild/
   lenovo$ ssh ledbox 'cd /home/pi/flushBuffer-rebuild && sha256sum -c SHA256SUMS'      # two OK
   lenovo$ ssh ledbox 'cd flushbuffer-src && ./build.sh'          # last lines: ldd = stock libs only
   ```
   then the README's switch-over. Expect: the panel identical to before (no garble, no flicker), and a
   brightness change in the console lands without the panel going dark. If garbled: the README's roll
   back, at once.
2. **Measure the refresh** (with §10.5 in effect):
   ```bash
   lenovo$ scp firmware/flushbuffer/measure-refresh.sh ledbox:
   lenovo$ ssh -t ledbox 'sudo ./measure-refresh.sh -t 60'
   lenovo$ ssh -t ledbox 'sudo ./measure-refresh.sh -t 30 slowdown=4 slowdown=3'   # A/B — LOOK at each run
   ```
   Without the script: `sudo killall flushBuffer2` then run `bin/flushBuffer2 ../www/buffer.png <the
   startled flags> --led-show-refresh` by hand for 60 s, Ctrl-C, `sudo ./stopled` and let the watchdog
   restart it. Expect: the estimate is ~90–120 Hz at slowdown 5. Any setting that garbles, ghosts or
   flickers on the glass is out, however fast it measures.

   at 1/500 s this panel will show bands — expected.
   Undo: `cp -a setting.ini.bak-20261023 setting.ini && sudo /home/pi/ledbox/bin/stopled`.
