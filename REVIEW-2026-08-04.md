# point-hub review

## Root causes worth fixing once

Several findings below are the same bug wearing different hats. Fix the cause, not the symptoms:

- **A. `/api/logs` has no byte budget.** One unauthenticated route with a 1 MiB body cap, a count-only rate limit, and no truncation anywhere downstream produces the heap bomb, the SD-card write storm, the log-rotation churn and the prototype-key filter bypass. Four findings, one fix.
- **B. `web/index.html` has no output-encoding discipline.** Two `innerHTML` string-concat sinks (match id, team colour) next to code that correctly uses `textContent` and `el.style.color`. Both XSS findings die if those two sinks are converted.
- **C. Shell scripts run `set -uo pipefail` with no `-e` and print unconditional success.** Five ops findings (SSH lockout guard, root check, install source, xtables lock, deploy verify) are all "command failed, script said OK".
- **D. Board state is in-memory only and never reloaded at boot.** `new sport.Source()` (`src/appliance.js:108`) starts neutral, `defaultIdle: true` (`:95`) paints the crest, and `resume.get()` is only ever called from an explicit `POST /api/game` (`src/controlServer.js:517`). Every crash-and-restart finding inherits its severity from this.

## High

**1. Unauthenticated `POST /api/logs` is a remote OOM** — `src/controlServer.js:614`, `src/logStore.js:143`
*(merges `unbounded-ui-log-msg-heap`, `unauth-log-memory-bomb`, `logstore-no-entry-size-cap`)*
No PIN, 1 MiB body, `msg` stored verbatim in a ring capped at **2000 entries, not bytes**; `safeData`'s 600-char clip only touches `data`, and its per-node caps have no total budget (a 40×40×40 tree survives intact at ~6 MB retained). Measured: 59 accepted 1 MB posts took RSS 67→169 MB and wrote 15 MB to `data/logs/`. Missing `level` defaults to `error` (`:613`), which force-flushes `appendFileSync` per post. Board dies in minutes; `Restart=always` brings it back at 0-0 (cause D).
**Fix:** `.slice(0, 300)` on `msg` at `:614` *and* in `LogStore.log`; a dedicated ~8 KB body cap for this route instead of `MAX_BODY`; a total-byte ceiling on `entry.data`; per-IP rather than global `uiRate`.

**2. `StreamDecoder` is per-client, not per-connection** — `src/ledboxClient.js:132`
A mid-message disconnect leaves a truncated gzip member in `decoder.buf`. The `close` handler resets `ready`/`socket`/`currentLayout` but never the decoder, so the next socket's bytes append behind it. The resync at `src/ledboxProtocol.js:54` only fires when `buf[0] !== 0x1f` — it is `0x1f`. Every reply is invisible forever, `ready` never returns, panel frozen, systemd sees a healthy PID. `mockLedbox.js:41` already does it correctly.
**Fix:** `this.decoder = new StreamDecoder()` at the top of `connect()`; cap `buf` at 64 KiB and force a resync on overflow.

**3. Layout guard stalls the send queue 5 s every 20 s** — `src/ledboxClient.js:726`
`setLayout(this.layout)` with no `timeoutMs`, so the default 5000 applies — and per your own `PROTOCOL.md:162-167` the device stays **silent** for a SetLayout to the layout it already has. `send()` is strictly serialized, so ~25% of scored points paint up to 5 s late and the ack blink collapses to one toggle.
**Fix:** `this.send('SetLayout', this.layout, {}, { timeoutMs: 800 })`, or probe with `GetLayout` (which does answer) and only re-assert on disagreement.

**4. A minus-button correction does not undo the set it awarded** — `src/manualSource.js:99`
`if (d > 0)` gates the whole set transition and nothing anywhere decrements `Sets` or pops `results`. Executed: 24-23 → `+1` → sets 1-0; → `−1` → points 24-23 but **sets still 1-0**; → `+1` → **sets 2-0 with two identical 25-23 pills**. Same gap lets both teams win one set (25-27 after a left win gives 1-1). The SET ENDED prompt is not modal (`web/index.html:142`), so the operator can press `−` while it is up. `src/beachSource.js:164-169` is identical.
**Fix:** compute `wonBefore`/`wonNow` for both signs; on `wonBefore && !wonNow` pop `results` and decrement `Sets`. Add a `setClosed` flag cleared by `next-set` so the losing side crossing the target cannot award a second set.

**5. Relay ping is sent but no pong is ever checked** — `src/relaySubscriber.js:52`, `:124`
No `_lastRx`, no liveness timeout; `default: break // pong ... ignored`. A half-open wifi socket stays `readyState 1`, no `close` fires, the reconnect at `:71` never arms. The UI has no signal either: `SourceManager` subscribes only to `state`/`error` (`src/sourceManager.js:41-42`) and `status()` never reports relay health. Panel sits on a stale score; TCP retransmission eventually breaks it in ~10-15 min, i.e. most of a set.
**Fix:** set `this._lastRx = Date.now()` on every frame and in `open`; in the ping interval, `if (Date.now() - this._lastRx > PING_MS * 2.5) this.ws.close()` so the normal reconnect path runs.

**6. Stored XSS via relay match id** — `web/index.html:1505`
`li.innerHTML = ... id ${m.id} ...` while the very next line uses `textContent` for the label. `src/controlServer.js:705` passes `id: String(m.id)` through from the relay unsanitised, and `/api/matches` (`:270`) has no `pinOk`. No CSP anywhere; the PIN is in `localStorage` (`:804`). Needs the attacker to occupy `RELAY_HTTP_URL`, hence high not critical.
**Fix:** empty `<div class="sub"></div>` + `textContent`; also `String(m.id).replace(/[^\w.-]/g,'').slice(0,64)` server-side.

**7. Empty `authorized_keys` guard fails open → permanent SSH lockout** — `provisioning/harden-board.sh:15`
Reproduced: `grep -c .` on an empty file prints `0` **and** exits 1, so `|| echo 0` also fires → `KEYS="0\n0"` → `[ ... -lt 1 ]` errors with "integer expected" and returns 2 → the `else` branch runs, prints "safe to proceed", writes `PasswordAuthentication no` and reloads sshd. A *missing* file works correctly; only the case the guard exists for fails. `provisioning/README.md:71` asserts the opposite.
**Fix:** `KEYS=$(grep -cE '^(ssh-|ecdsa-|sk-)' … || true); case ${KEYS:-0} in ''|*[!0-9]*) KEYS=0;; esac`.

**8. Board AP passphrase and vendor admin creds committed to a public repo** — `docs/hall-guide.html:76`, `:193`, `:196`; `STATUS.md:99`
*(merges `leaked-ap-passphrase`, `default-admin-creds-published`, `published-default-creds`)*
`ledbox_C0270 / wiedikon2026` in cleartext plus an embedded Wi-Fi QR PNG — the exact artefact `.gitignore`'s `firmware/**/wifi_qr.png` block exists to keep out. `git log --follow` shows the file entered in `81aecf9` (2026-08-04), *after* the 2026-08-02 rotation `STATUS.md:100` records, so this is the current passphrase. `provisioning/ledbox-firewall.sh:57-60` deliberately does not rate-limit wlan0, so RF range = unthrottled :8890 (see finding 1). Same file publishes `192.168.5.1 · admin/admin`, unchanged vendor default; `harden-board.sh:52` only disables apache2 and says so is one command to undo.
**Fix:** rotate the PSK on the board and in Vaultwarden, change the vendor panel password, replace both with pointers the way `STATUS.md:100` already does, purge from history (public repo), and gitignore `hall-guide.html` as a generated handout. Add `-A LEDBOX-IN -p tcp --dport 80 -j DROP` for wlan1/eth0 so a debug re-enable of apache2 doesn't republish the panel.

## The single most dangerous thing

**The board has no durable notion of "the current match", so any restart silently resets the score — and there are many cheap ways to force a restart.**

`src/appliance.js:108` constructs `new sport.Source()` neutral, `:95` sets `defaultIdle: true`, and `resume.get()` is *only* reachable from an explicit `POST /api/game` (`src/controlServer.js:517`). So a bridge that restarts at 22-21 comes back showing the KSCW crest with 0-0 behind it, and stays there until a human notices and clicks Continue. The unit is `Restart=always`/`RestartSec=5`, so this is not a one-shot: it loops.

What makes that dangerous rather than merely annoying is how many unprivileged paths reach it. A phone in RF range of an AP whose passphrase is on GitHub (finding 8) can OOM the process with a `curl` loop against an unauthenticated route (finding 1) — no PIN, no LAN access, no exploit. And the failure is invisible in the right way: `systemctl is-active` says `active`, the deploy script says `DONE`, the tablet shows a live-looking scoreboard (`web/index.html:1415`), and the only place the truth appears is a log file you'd have to be looking at.

Rank the fixes accordingly: cap `/api/logs`, then auto-load the resume slot at boot (`if (resume.get(sport)) …` in `appliance.js` before `ledbox.connect()`), then rotate the passphrase.

## What is missing entirely

**Nothing tests the appliance as an appliance — no test in `npm test` ever starts an HTTP server, and no test ever breaks a connection.**

Of 11 scripts in `package.json:13`, not one imports `src/controlServer.js`. The single test that boots the real thing (`test/appliance-selftest.mjs`) is excluded from `test` and has been silently failing on any machine with a PIN set. Every client in the suite is `reconnectMs: 0`, and no test destroys a socket. The five inline selftests that *do* cover the scoring rules are orphaned — I removed the win-by-two condition from `src/manualSource.js:104` and `npm test` stayed green at exit 0.

The consequence is that the entire class of "the board survives an interruption" is unverified: PIN enforcement on 14 endpoints, the repaint-after-reconnect at `ledboxClient.js:176-181`, the resume-clear-on-match-end branch, `historyStore` in its entirety, and the shutdown path. Every one of those is a live-match property, and every one of them is currently guarded by nothing but the fact that it was written correctly the first time.

Three additions, in order of value:

1. `test/control-auth-selftest.mjs` — boot `createControlServer` on port 0 against a temp settings file; enumerate every mutating path and assert 403 unauthenticated, 200 with the right PIN, 429 after six wrong ones, and 200 on `GET /api/status` with no header. This is the test that makes a new endpoint added without `pinOk` fail the build.
2. A reconnect case in `mapper-selftest.mjs` — push 22-21, `client.socket.destroy()`, await the second `ready`, assert the mock panel *still* reads 22-21 on the match layout. That is the blank-board-mid-match property, and it currently has zero coverage.
3. Append the five inline selftests to `test`. One-line change; all five pass today.

Add a chaos-shaped fixture while you're there — a mock that truncates a reply mid-gzip and one that goes half-open without a FIN. Those two behaviours are findings 2 and 5, and both were found by reading rather than by running, which is the gap.
